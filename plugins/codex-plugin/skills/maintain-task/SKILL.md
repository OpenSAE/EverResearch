# Maintenance of research tasks

## Run bundled ResearchHarness commands

When a step calls for an `rh` command, run this skill's `scripts/rh.py` with Python
3.11 or 3.12 and pass the arguments after `rh`. For example, for a project check
run `python3 <absolute-skill-path>/scripts/rh.py projects project check <project-path>`.
Resolve the skill path from the current SKILL.md. On Claude Code and Cowork use
`${CLAUDE_SKILL_DIR}` for that directory, and on Claude web use the script staged in
the skill directory. Use an already available Python interpreter or let uv
select one if the host provides uv. The launcher uses the bundled OpenSAE wheel
and prepares a private Python environment automatically on first use. It may
fetch Python dependencies from the package index. Continue with file review if
the host cannot run Python or prepare the environment. State which automated
checks were unavailable. Never install the similarly named PyPI package.

## Automatic precheck before running a formal task

The project must provide a precheck capability called `precheck` under `tasks/` to accept any registered data set, model and task selection and to indicate the specific reasons for incompatibility.

For each official start-up task, the entry is automatically called before the formal calculation starts after the effective configuration and component selection is determined `precheck`.The same precheck is carried out for all the actual tasks at the different entry points and batches. After the precheck, the precheck automatically enters the formal computation. `precheck` Run the precheck itself directly from time to time.

The precheck uses the data set, model, task and operation configuration selected at the time. The prechecks quickly walk through actual data reading, model architecture and necessary weight loads, minimum calculation of tasks, and result writing and official rereading, using a small amount of representative real input and a very limited workload. The formal path generation and result is logical, the minimum sample is written in a separate location, the planned drop point, the actual relative path, the file name, the format and the necessary field. The prechecks only perform the required start-up check, with the sample numbers, calculated steps and the written amount kept in line, and the prechecks are kept separately from the official results.

## Validation criteria

- Confirms that the precheck is automatic from the regular mission entry. Only a small number of inputs are processed and completed quickly with a runable group confirmation precheck, and errors are located with a clearly faulted combination that the formal computation has not yet started. The check prechecks are generated by formal writing rules and can be opened by the official reader.
- When the task entry point, precheck, or its blocking logic changes, verify a successful run and a rejected run through the normal entry point. Share those results with experiment maintenance. Saves a record of success and precheck failure at normal access. Use a central command when the record format supports `rh projects precheck check <project root directory> <Directory of successful execution> <Synchronising "%s"> --max-seconds <seconds> --max-samples <Number>` Checks the total time between start-up and precheck, the number of samples processed, the failure block and the test path.
- Enter a sample, construct a model, calibration, and output and consumer. Borders or incompatible scenes should give identifiable results or errors.
- When assessing, describe the unit of account, the actual inclusion and exclusion, the manner of aggregation and the questions answered by the indicator.
- A two-way inventory of tasks and subtasks from registration, project installation package, manual commands, scripts and product testing. An independent public entrance is also registered to the mission document. Distinguishing training, re-evaluation and reporting under the same objective, and determining the sub-task level by input and actual product.
- Attribution along import checks. The tasks and product tests that can be installed are achieved by a formal mission, data, model or operating package, with manual scripts calling from the outside. When there are multiple entry points for the same calculation or the same result agreement, the actual behaviour retained at each entry is uniformly achieved and verified. The task document, the source layout and the operational entry should be able to search for each other.

## Item-by-line

The sub-missions can be independently called. The attribution checks which input it relies on, which operational product it uses, what it delivers, and by whom it continues to read. There are multiple tasks for which the operation is provided in a single module. The existing commands can continue to point to the same achievement.

The research logic for the sub-task of the same task is placed in the name module of the task. When cross-task reading of the sampler and label, tectonic model, restoration of the training status or serialization file, the data, model, and the performance of the operating layer are reused separately. When a directory is found to be clustered only by the reuse relationship, the object, the actual caller, and the rules it maintains are identified and placed in the position of the responsible object.

For projects using a layered configuration, each sub-task has its own parameter prefix, reflecting the task and sub-task name. Only the value that changes the result or execution mode in the sub-task enters the prefix. The choice of multiple sub-tasks is provided by task integration, and the document lists the reuse relationship and the conditions of validity.
