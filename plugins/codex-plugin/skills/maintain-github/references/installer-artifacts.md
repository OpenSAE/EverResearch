# 发布安装产物和更新下载入口

## 目的和主要功能

用 Git 保存源码和插件发现所需的文本，用 GitHub Release 附件交付各版本的安装文件。检查新旧安装地址，避免二进制随版本写入提交，也避免用户安装中断。

## 适用范围

适用于发布 wheel、npm tarball、插件 ZIP、示例包及其校验文件，或者把已有的下载产物从 Git 迁移到 Release。源码发布、附件发布和历史整理分别按用户授权执行。

## 源码、插件副本和发行版本核对清单

1. **记录三处实际状态。** 查明本地源码、GitHub 目标提交和最新公开发行。核对 `pyproject.toml`、`CITATION.cff`、变更日志、中英文安装命令，以及公开标签和附件。回退发行或合并后重新比较本地与 `main`，列清残留版本字段和指向失效版本的链接，按用户指定的版本对齐。
2. **同时检查技能源文件和分发副本。** 对照 `.agents/skills/` 与各平台的 `plugins/*/skills/`，校验技能入口、被引用的配套文件及平台索引。在日常更新中，从同一份源技能同步仓库内的分发副本，保留已发布的插件版本、运行时锁和附件。技能需要已发布运行时缺少的功能时，在分发副本注明实际限制和可用的源码入口。
3. **确认推送的实际影响。** 读取目标分支的工作流及版本判断，确认推送会触发哪些检查和发布动作。日常更新保持发行版本。正式发布以用户本次批准的版本为准，推送前确认版本、标签、运行时校验值和分发渠道一致。
4. **推送后回查。** 记录实际提交和版本，从公开仓库验证技能清单与安装入口，执行适用的首次启动检查。对照公开 Release 标签，区分已更新的仓库副本、正在使用的运行时与固定版本附件。

仓库包含 Git LFS 文件时，插件安装检查应覆盖启用了 Git LFS 的环境。使用平台支持的稀疏检出，仅拉取市场清单和所需插件目录。使用会检出整个仓库的工具时，插件安装应跳过与插件无关的 LFS 下载。同步研究模板本身时，另外核对每个保留的 LFS 指针在目标仓库有可下载的对象。

## 发布前核对

1. 在技能的发布副本或项目已有构建目录生成安装文件。对照 git diff --cached --name-status 和目录实际字节数，确认源码提交的新增内容是源码、说明、清单及插件发现所需的文本。版本化的构建产物默认全部作为 Release 附件。
2. 记录版本、真实源码提交、附件文件名和 SHA-256。确认源码标签指向该提交。使用版本固定的附件地址，避免 latest 与已安装插件的版本或哈希发生错配。
3. 首次迁移时，搜查 README、宿主安装说明、启动器以及历史发行版的下载地址。已安装插件使用的旧地址需要兼容。先为每个版本上传可用的 Release 附件，随后才修改入口或移除主分支的二进制文件。清理既有 Git 历史需要单独授权。

## 同步更新已授权的版本

1. 发版前核对 PyPI、GitHub Release 和仓库中的实际版本。如果用户指定的版本已有同名安装文件，保留原发行物，说明占用情况并取得对新版本号的明确许可。源码更新可以按已有授权继续。
2. 从同一个确认的源码提交构建一次。把同一份 wheel 用于 PyPI、GitHub Release 和插件分发。用实际公开可下载的文件核对 SHA-256 和大小，再同步全部平台的插件副本、`rh-runtime.json`、目录清单、安装文档和版本说明。
3. 从公开渠道核对终端安装和插件首次启动，确认它们加载相同的新版本并能执行本次改动。用空缓存验证首次安装，再检查复用缓存。源码测试和单个渠道上传成功只算阶段结果。所有目标渠道验收通过后再汇报发版完成。

## 验收和交付

1. 用未登录的环境下载新附件，将文件的 SHA-256 与构建记录对照。确认所有用户可见的入口都指向同一版本和可用附件，包括 wheel、npm tarball、插件 ZIP 和示例文件。
2. 从公开地址实际运行安装命令。插件首次运行需要下载解释器组件时，使用空缓存验证下载和校验，再验证缓存复用。替换旧入口时，按实际保留的兼容路径检查已有安装。
3. 回查 GitHub 主分支的暂存清单和发布提交，确认没有新增版本化二进制。报告发布版本、下载链接、已通过的平台，以及由于执行环境不同未覆盖的部分。用测试的真实运行环境描述结果，例如区分 cgroup v1、v2 和模拟测试。
