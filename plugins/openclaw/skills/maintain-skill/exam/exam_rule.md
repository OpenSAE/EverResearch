# 项目维护方案考题

## Purpose and main function

建立可重复使用的项目维护题库。通过真实项目需求，观察子代理能否自己找到负责的功能、判断文件归属和依赖，并提出可复核的改动方案。

## Scope of application

用于 SpatialPheno、GeneReasoning 和 SAEBase 的方案阶段考察。每个项目覆盖十项职责，每项设计三道独立题，共九十题。本页规定出题和评阅方法。实际题目基于出题时可读的项目版本，子代理只读项目并交付方案。

## 考卷命名与范围

具体考卷使用 `exam_<project>_<purpose>.md`，例如 `exam_spatialpheno_maintenance.md`。项目段使用项目名的小写写法，目的段使用一个能说明考察用途的英文词。每份考卷由本规则出发，只覆盖一个项目，所有题卡使用同一个真实项目名。不同项目分别成卷。考卷和评阅记录留在本机，规则和忽略设置随技能维护。

## 根据项目的实际功能出题

先确认项目根、维护模式、公用入口和项目版本。沿现有命令、配置、源码和结果查清该项目有哪些真实的科研操作。每题选择一个实际可识别的研究对象或日常用途，并确定用户想看到的变化。题面可以写现有工作流、结果名称、用户可见参数或研究条件，路径和代码归属由子代理自己查明。项目入口或必要材料缺失时，在评阅记录标明缺少什么。

三个项目使用同一覆盖表，各自选择真实场景。每项的三题应有不同的维护目标，能暴露不同的职责判断。把下表留给出题人和评阅人。子代理只收到一张中性的题卡，其中写项目名、目的和固定作答方式。题卡省略技能名、目标目录名、应改文件、预期操作步骤和标准答案。使用用户能够直接提出的需求，例如「用已有评估结果生成一张可复用的模型对比图」。

| 功能职责 | 第一题 | 第二题 | 第三题 |
| --- | --- | --- | --- |
| 数据集 `datasets` | 增加一种数据来源、子集或数据预设 | 缩减现有数据范围或停用一种选择 | 改变样本准备、标签或划分方式 |
| 模型 `models` | 增加有明确用途的模型变体 | 停用一种不再提供的模型变体 | 改变现有模型的结构、权重选择或接口 |
| 科研任务 `tasks` | 增加一种科研计算或评估 | 收回一项已有任务或一条任务入口 | 改变任务流程、前置检查或结果契约 |
| 实验 `experiment` | 用现有组合开展一次新实验 | 清理一项已明确停用的旧实验，交代历史引用 | 改变现有实验的产物生成或读回方式 |
| 操作工具 `scripts` | 从现有结果生成可反复使用的图表 | 收敛同用途的重复手工操作 | 为既有研究设置一组可重复的参数搜索操作 |
| 验证 `tests` | 为一条缺少覆盖的公用入口设计完整性检查 | 精简重复的检查并保留其覆盖 | 调整现有检查以覆盖失败场景或兼容要求 |
| 长期资源 `assets` | 把供多次任务复用的已准备输入纳入项目资产 | 处理不再使用的旧资源，交代现有引用 | 更新或替换仍在使用的参考资源或已准备输入 |
| 临时工作 `tmp` | 做一次探索性尝试，明确成果只供本轮参考 | 清理一次已结束的尝试留下的材料 | 为当前讨论准备一次性诊断输出或说明 |
| 项目文档 `doc` | 阅读现有说明并为一项用途补齐缺失说明 | 找出并精简重复或失效的说明 | 根据实际入口和结果修订现行说明 |
| 配置 `conf` | 增加一个用户可设置的参数 | 收回一个可调参数并将其设为常量 | 改变现有参数的默认值、含义或覆盖行为 |

对于绘图和参数搜索，只描述用户要完成的操作。对于临时工作，在目的中明确产物只用于本次尝试。对于文档题，要求先读懂相关页面，再根据任务说明提出增补、删减或修订方案。每题只设一个主要目标，允许方案指出有证据支持的跨职责影响。

## 固定题面格式

```text
项目：<实际项目名>
目的：<用自然语言描述希望实现的结果和必要条件>
方式：请不要直接改动文件，而是最后给一个方案，讲述你的思路，明确你要改动的文件和范围，并且不要实施改动。
```

题卡中的「目的」描述假设要完成的工作。「方式」限定本次只提交方案。即使目的是新增、删除、训练或改变结果生成，也通过行文说明预期效果和范围，实际操作留到另行授权的阶段。

## 发题与观察

1. 给每道题建立干净上下文和中性的任务名称。让子代理能按普通入口读到目标项目与技能，只给它固定格式的题面。评阅记录、预期归属、故障列表和同题旧答案留在出题人一侧。此处属于需求题方案考察，技能选择由子代理自己判断。
2. 子代理可以只读核对项目。禁止本轮造成项目、中央仓库、数据或外部服务的变更。训练、安装、下载、生成产物和会写入的测试均只写入拟议方案。保留子代理主动展示的入口、事实依据、当前路径、计划路径、文件改动类型和验证方式。若它主动说明使用了某项技能，可以记录为观察证据。
3. 重测时保留题面、项目版本、适用规则与可用资源。每道题使用新的子代理。项目状态变化时记录差异，并按相同条件比较可比部分。

## 监考与学生分工

每场考卷由一名独立的监考官子代理负责。监考官持有该卷、项目版本和评阅规则，准备评阅依据、发放题卡、收集答案并逐题评阅。每道题使用一名新的学生子代理。一场有三十题，就有三十名相互独立的学生，同一学生只答一题。各学生使用干净上下文和中性任务名，只收到本题题卡。

并发名额有限时，监考官分批启动学生。每批留出学生席位，前一批结束后再启动新学生。不同考卷可依次进行，每场始终有自己的监考官。保持题号和学生的一一对应，记录中断或无法取得证据的情况。

每收到一份学生的最终答卷，监考官立即将原文保存在本机 `exam/` 下本场独立的记录目录中。用题号保存答卷，例如 `question_01.md`，并在本场记录中登记题号、学生标识、完成状态和原文路径。保存原文后就核对该题的逐文件清单，将评语与学生原文分开。材料未收到或无法读回时记录实际状态。复评时从保存的答卷读回原文。学生继续只收到三行题卡。

监考官向主代理提交整场汇报。汇报包括每题的判断、事实依据和方案遗漏，汇总通过、部分达到、未达到和证据不足的数量，并指出反复出现的技能触发、文件归属或验收问题。评阅材料留在 `exam/`，由主代理核对并向用户交付。

## 逐题汇报拟改文件

监考报告每题必须包含学生方案中的文件改动清单。新增和修改文件逐项列出，分别保存其完整路径及拟新增、修改的具体内容。目录级说明可作为上下文，文件级条目应说明计划新增的功能、改动的逻辑、配置项、文档内容或验证用例。保留学生实际提出的范围。删除、移动和重命名也按项写清楚，移动或重命名同时记录原路径和目标路径。

| 操作 | 当前路径 | 拟新增或改动后的路径 | 学生拟改的具体内容 | 监考官对路径和内容的判断 |
| --- | --- | --- | --- | --- |
| <新增、修改、移动、重命名或删除> | <原路径，新增可填不适用> | <明确的项目内相对路径或绝对路径，删除可填不适用> | <具体改动及放在此文件的用途> | <分别判断位置和改动是否合理，并给出依据> |

同一题有多个文件时逐项记录。学生明确提出复用已有实现或无需改文件时，记录该判断及其依据。答卷只有目录、未给文件名、未说明改动内容，或原答卷无法读回时，逐项标明缺失和评阅影响。监考官如需补充建议，另行注明是评阅建议，保留学生原方案的边界。总评或通过标签不能替代逐题文件清单。

## 按实际证据评阅

| 评阅项 | 判断依据 |
| --- | --- |
| 理解目标 | 方案满足真实需求，说明可核实的前提和仍需确认的决定。 |
| 找到职责 | 有证据表明它找到了实际入口、生成器、读取者和负责的功能。自行选对技能可以支持判断，技能名本身不构成通过证据。 |
| 路径和范围 | 逐项给出实际存在的当前路径、拟改或拟新增的文件路径、具体内容、操作和原因。迁移方案交代现有调用、历史结果和原始输入。 |
| 发现遗漏 | 能沿同一入口识别相邻消费者、默认路径、缺失证据或其他会影响目标的问题。报告具体文件和影响。额外发现按证据判断。 |
| 可验证性 | 指出未来要走的公用入口和可观察结果，覆盖此题涉及的默认或异常情况。把已核实事实和拟执行检查分开。 |
| 只交付方案 | 项目和外部服务保持只读。实际改动、删除、训练或写入即违反答题方式。 |

按题记录通过、部分达到、未达到或证据不足，并给出具体依据。预先保存评阅预期，允许经证据支持的其他方案。待同类问题在不同项目或题目中重复出现时，检查负责技能的触发、判断和验收说明。改动通用技能后，用同题或等价题重新考察，把具体项目的路径与结论留在评阅记录。

需要检验子代理是否能实际修复项目时，转入 maintain-skill 的独立项目维护测试。该测试按已有的两行指令和执行授权进行，与本页的方案考察分别记录。
