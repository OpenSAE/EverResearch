# Maintain GitHub — 把选定内容发布到 GitHub

## Run the EverResearch CLI

Use Python 3.11, 3.12, or 3.13 to run `scripts/rh.py` from the current skill,
followed by the arguments after `rh`. For example, pass `projects project check <project-path>` to check a
project. Use `${CLAUDE_SKILL_DIR}` in Claude Code or Cowork and the staged skill
directory in Claude web.

The launcher uses the packaged runtime when available. GitHub marketplace
installs download the pinned wheel once and verify its checksum before use.
The launcher creates a private environment and may fetch Python dependencies.
With no Python execution available, review the files you can
access and tell the user which automated checks you could not run.

For a separate terminal installation, the official PyPI package is
`ever-research` from OpenSAE. The PyPI project named `researchharness` is
maintained separately.

## 目的和主要功能

帮助用户把整个项目、某个目录或几个文件发布到 GitHub。先说清发布什么、放到哪里，再把选定文件复制到本技能内，准备可查看的变化，并按用户授权完成发布。

提供对照检查模式：先确定每个管理项目的本地路径、GitHub 位置与比较范围，再说明两边的文件和内容差异，供用户决定是否对齐。

原发布对象始终保持只读：文件内容和文件集合保持原样。Git 仓库、发布说明、版本包、临时文件和日志都在本技能内准备，实际上传来自内部副本。

## 适用范围

用户要求将选定内容发布或更新到 GitHub 仓库、通过合并请求（PR）提交变化，或制作和发布版本（Release）时使用。用户只要求讨论方案或查看待发布变化时，按该范围准备。

用户要求对照 GitHub 管理的项目与本地技能、查看两边差异或讨论是否对齐时，使用对照检查模式。

支持 GitHub.com。运行使用 Python 3.11 及以上版本、Git 和 GitHub 命令行入口 `gh`；仓库发布需要已有的 GitHub 登录或环境中的凭据。所需工作说明与程序均在此文件夹内。待发布项目是读取对象，GitHub 是用户指定的发布目标。

## 必须遵守的书写与交流规则

以下原文复制自 EverResearch 根目录 AGENTS.md 的“书写、解释与对话原则”，作为本技能内必须遵守的规则。使用本技能起草、修改或翻译 README、其他 Markdown、合并请求说明和版本说明，以及向人类解释和汇报时，均遵循这些原则。英文和中文采用相同的表达要求。

### 7. 书写、解释与对话原则

本原则适用于书写文件、向人类解释问题和与人类沟通，目的是确保人类能够理解所写、所说的内容。

1. **使用常见词语。** 将代号、生造合成词和需要专业背景才能理解的词语，改为常见、直白的表达，直接说明具体对象、作用和结果。
2. **使用完整的自然语言。** 缩写和代码表达统一改为完整词语与人类可以直接理解的说明。
3. **用肯定句说明概念与关联。** 直接说明每个概念的含义、作用、相互关系及适用情形，概念区分与边界说明一律采用肯定句式。
4. **按人类需要提供细节。** 日常书写和交流以理解实际问题、用途和结果为主；技术细节与执行边界在人类明确要求时再展开。默认将执行边界的模糊之处和技术细节的描述缺失视为对任务影响轻微的情况，按现有信息继续处理。

## 选择本次工作方式

发布模式按下文准备副本、展示变化并执行获准发布。对照检查模式先确定项目路径与范围，再读取两边资料并报告差异。沿用用户已经选定的模式；同一任务涉及多个项目时，分别确定各项目的对象与范围。

## 对照检查模式

### 明确项目路径与范围

每个要管理的项目都明确以下信息，已有记录供本次选择参考，实际操作采用当前确认的对象：

- 本地项目或技能的完整绝对路径，以及本次比较的目录和文件。原始技能、发布副本和其他安装副本分别以实际路径标明。
- GitHub 仓库地址、分支或版本，以及仓库中的对应目录。分支采用用户选择；用户只提供仓库时，使用仓库当前默认分支并说明实际选择。
- 本地与 GitHub 的路径对应关系，例如本地技能目录对应仓库根目录。
- 纳入和略过的内容，例如是否比较 `results/`、缓存、历史资料，以及只在发布副本中增加的 README 和许可证。沿用用户已明确给出的取舍。

先读取已有任务记录和当前目录，找到真实路径与现有对应关系，再集中询问影响比较的缺失信息。用户要求加载技能或准备管理项目时，先明确路径与范围；需要了解两边是否一致时再进入比较。

### 比较并说明差异

将本次选定的本地文件复制到技能内部，并在同一任务内读取 GitHub 的指定版本。记录本地来源、范围、路径对应关系和实际远程提交，使结果对应本次读取的内容。比较过程保留两边原始内容。

按路径对应关系比较两边选定范围内的全部文件，说明本地独有、GitHub 独有、内容不同的文件，以及影响使用的可执行属性变化。文本差异结合实际内容解释具体含义，二进制资料说明文件与内容是否相同。发布时有意增加、翻译或略过的内容，按已有依据说明用途；原因待确认时标明待确认。

现有 `prepare` 用于准备发布变化。对照模式另行比较两边的文件清单，覆盖 GitHub 独有文件。具体操作见下文引用的“准备、发布与保存”。

### 请用户考虑是否对齐

先简短说明整体是否一致，再列出实际差异及其影响，请用户考虑保留各自版本、以本地为准更新 GitHub、以 GitHub 为准调整本地，或只对齐选定内容。建议结合各文件的实际用途说明。

对齐决定应明确方向、涉及的文件和预期结果。用户作出决定后，按选定方向准备具体修改，并依据对应操作的授权实施；原目录沿用本技能的只读规则，本地调整先准备内部副本与具体差异，原目录的实际修改通过目标项目的维护流程处理。当前任务只要求比较时，以差异说明和待选择事项结束。

## 先确定发布什么

沿用用户的语言，用清楚的功能说明交流。先讲“发布哪些内容、别人怎样使用、会改变哪里”，实现细节在用户询问或影响选择时说明。

用户已明确指定目录或文件时沿用该选择。尚未指定时，轻量阅读当前目录和已有说明，推荐几个实际入口，给出用途与完整路径，等待用户选择。例如：

> 我可以帮你把选定内容发布到 GitHub，原文件保持原样。你想发布整个项目，还是其中某个目录或几个文件？
>
> 1. <目录 A>：<对外提供什么能力>。文件在 `/完整路径/A/`。
> 2. <目录 B>：<对外提供什么能力>。文件在 `/完整路径/B/`。
> 3. <当前项目>：发布当前项目的选定内容。文件在 `/当前项目完整路径/`。

根据选定内容，说明建议带上的文件和准备略过的内容。运行结果、临时资料和本机配置是否纳入，以用户确定的范围为准。程序会略过 Git 自身资料，并在选择父目录时略过本技能的运行产物，防止把正在生成的副本再次复制进去；明确选择某份已有产物时可单独纳入。

### EverResearch 的发布筛选规则

发布或扫描 EverResearch 时，对 `.agents/skills/` 和 `src/` 使用同一套判断。根据文件的实际用途、内容和调用关系决定范围。

- 保留通用原则、项目管理方法、共享代码、通用配置、模板、测试及其可复用的样例和素材。
- 排除实际运行结果、导出件、发布副本、会话和操作日志、缓存、草稿及其他临时文件。排除具体项目的登记、绑定、数据与模型路径、运行记录、结构审查结果和项目专用说明。
- 用某个项目讲解通用方法时，保留方法和供复用的部分。文件同时含有通用规则和项目专用信息时，扫描中标出位置，先在发布副本中准备清理方案。

先按实际用途检查文件，再核对现有 `.gitignore`。扫描报告指出应排除但仍可被 Git 纳入的内容、应保留但被忽略的内容，以及需要进一步判断的混合文件。发布准备时将确定的排除范围传给 `prepare --exclude`，同时核对发布副本、版本包和目标仓库的已追踪文件。修改忽略规则和清理已追踪内容分别按用户授权执行。

`prepare` 按映射和 `--exclude` 选择文件，再用 `git add -f` 暂存所选文件。执行整库发布前，把根目录和各子目录中适用的忽略规则纳入本次范围判断，并在准备后核对 `plan.json` 的文件清单。Git 的忽略规则和发布程序的排除范围需要分别核对。

### 其他发布对象的历史资料和结果文件

确定对象目录后、复制和准备发布前，轻量查看其中是否包含历史资料、备份、结果文件、日志、缓存或临时产物。目录名用于寻找线索，结合已有说明和必要的少量阅读解释实际用途；用途不足以确认时标为待确认。

发现这些内容时，列出相关路径并各用一句话说明保存什么，再向用户询问本次 GitHub 发布或 Release 的范围。给出贴合当前目录的建议，例如：

> 这个目录还包含 `history/`（旧版本资料）和 `results/`（已生成的结果）。这次发布你希望：
>
> 1. **只发布程序和使用说明**（建议）。
> 2. **同时带上选定结果**，由你指定哪些结果需要交付。
> 3. **全部纳入**，包括上述资料。

选项根据实际内容调整。等待用户确定后，将具体纳入和略过的路径落实到发布范围；用户已经明确决定这些内容时，复述实际范围并沿用决定。笼统指定整个对象目录时，仍按本节确认其中这类资料的取舍。

需要 Release 时，同时讲清仓库内容与下载附件是否采用相同范围。GitHub 自带的源码下载取自版本标签对应的整个仓库，上传的版本包附件可只包含选定文件。若用户要求排除已存在于目标仓库中的资料，先说明仅缩小附件范围仍会保留仓库中的文件，再确认是否调整仓库发布范围。所有范围调整均作用于内部副本，原对象保持原样。

## 确定发布到哪里

从当前任务和用户已提供的信息中确定以下事项，缺少实际必需的信息时集中询问：

- 目标仓库，是已有仓库还是新仓库；新仓库明确公开或私有。
- 文件放在仓库根目录，还是某个子目录；多个来源可以分别指定位置。
- 直接更新指定分支，还是提交 PR。
- 本次只发布内容，还是还需要带版本号和下载包的 Release。

例如，`ExtractStructure/` 的内容可以成为独立仓库的根内容，也可以放到已有仓库的 `skills/extract-structure/` 下。

默认发布当前选定内容的副本。保留原项目的提交记录、持续自动同步或部署网站属于不同需求，用户明确提出时再确定做法。

## 发布文档的默认语言

一般默认以英文发布面向读者的 Markdown，用户明确指定语言时沿用该选择。与用户交流继续使用用户选择的语言。

发布内容的说明入口默认采用英文 `README.md`，同时提供内容对应的中文说明 `README.zh-CN.md`。两份文件的开头、正文介绍之前都放置语言切换链接，让读者可以直接选择英文或中文：

```markdown
[English](README.md) | [中文](README.zh-CN.md)
```

两种语言说明相同的用途、使用方式和必要条件，命令、路径和字段保持准确对应。其他面向读者的 Markdown 默认使用英文。已有文档采用其他中英文文件名时，沿用现有组织方式，使用实际相对路径连接两个版本；用户明确要求不同语言安排时按其要求处理。

起草、翻译、补充中文说明和添加切换链接均在本技能的发布副本内完成，原发布对象保持原样。准备差异时将英文说明、中文说明及其链接一并列入待发布内容；版本包包含本次选定交付的说明文件。源文件中由程序读取的格式、字段和标识保持现行写法，文档解释按上述语言要求整理。

## 准备内部副本并说明变化

1. 将选定文件实际复制到 `results/<任务标识>/source/`，保留内容和可执行属性。使用独立文件；目标项目的目录保持原样。
2. 在同一任务的 `checkout/` 准备目标仓库，把内部副本放到选定位置。首次发布可先在本地准备空仓库，创建 GitHub 仓库留到实际发布时执行。
3. 默认只新增和更新选定路径。删除目标仓库中的文件时，明确列出待删除路径及用户的对应授权。
4. 按上述默认语言要求准备发布说明，保存实际差异，用简短说明告诉用户将新增或修改哪些内容、目标仓库其他部分是否受影响。复制所需的依赖、补充其他文档、许可证或调整版本号等，先说明实际需要；获准后只在技能内的副本上处理，再重新准备差异。

源文件夹中保持原样的内容包括 `.git`、README、许可证、版本号、打包文件和运行结果；发布所需的新增文件全部位于技能内。构建命令和其他可能写文件的操作使用内部副本作为工作目录，输出、临时文件和缓存也指定在内部。

需要调用程序或准备对照检查时，阅读[准备、发布与保存](references/commands.md)。该文档的目的和主要功能：说明发布程序的命令、文件范围、内部副本、差异和结果保存方式。同时说明如何在技能内部准备本地与 GitHub 的比较副本，覆盖两边文件集合并记录差异。适用范围：执行目录或文件复制、仓库发布、合并请求（PR）、版本包或版本发布（Release）操作时使用。此文档供智能助手调用内部程序，对用户的交流沿用 SKILL.md 中的功能语言。对照 GitHub 项目与本地技能、准备比较副本和查看差异时，同样使用本文件。

## 按已确认范围发布

展示变化后，沿用用户已经明确给出的发布授权。只有目标、公开范围、删除内容或发布行为尚未获得授权时，才补充询问缺少的决定。准备工作完成后再请求实际发布的批准，使用户能看到具体结果。

### 部署前核对目标环境

发布会自动触发部署，或本次任务包含手动部署时，在推送或触发部署之前，确认目标仓库、分支、部署流程和目标站点。读取目标分支上的部署配置和依赖版本文件，结合部署平台当前的支持说明，核对实际运行镜像、运行时与构建工具版本，以及项目依赖能否在该环境中安装。部署依赖环境变量或密钥时，只核对配置项是否就绪。

使用 `ubuntu-latest` 等会随平台更新的标签时，确认它当前对应的镜像和项目固定版本是否兼容。例如，学术网站指定 Ruby 3.3.5，`ubuntu-latest` 切换到 Ubuntu 26.04 后，该版本无法安装，网站改用 Ubuntu 24.04 完成部署。发现同类冲突时，先在授权范围内修复并重新核对环境，再执行部署。将确认的环境、发现的问题和修复结果记入本次任务记录。

实际发布只使用已准备的内容。内部副本、待提交内容或远程分支发生变化时，说明变化并重新准备；本次已展示的内容和发布授权相互对应。

发布失败时记录实际完成到哪一步，保留内部副本。先查看本地结果与远程状态，再决定沿用已有资源、重新准备或继续创建。程序使用普通推送，远程冲突保留给下一次明确处理。

建立 PR 后，如当前宿主提供 PR 附件工具，将真实 PR 链接附到当前任务。此能力只用于交付链接，技能的准备和发布流程使用自带程序即可完成。

## 交付与保存

完成后返回真实的提交、PR 或 Release 链接，用一两句话说明发布了什么。只制作本地版本包时，返回内部文件的完整路径。发生部分失败时，分别报告已完成和待处理的操作。

全部本地产物保存在本技能的 `results/<任务标识>/`。任务记录说明发布来源、文件放置位置、实际差异和已完成结果；GitHub CLI 负责认证，任务结果保存提交或发布状态。

测试、浏览器验证和额外源码修改按用户明确要求处理。每次外部写入均以用户对具体发布任务的授权为依据。
