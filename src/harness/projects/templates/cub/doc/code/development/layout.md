# Examples of layouts of CUB classification templates

## Purpose

Corresponding the central catalogue rules to the operational classification, indicating which directories are used in the template and how they will be expanded if additional uses are made.

## Scope

To create projects, add components or adjust layouts by reference to templates. The Central Workspace uses the [Scientific Project Catalogue and Documentation](../../../../README.md#project-layout) to determine the conditions, duties and designations of the first-level layout, the second-level directory.

## Actual location and enable conditions

The root catalogue of the independent research project provides both `base/`, `datasets/`, `models/`, `tasks/`, `conf/`. Run `rh projects project check <project-root>` to check the actual realization of the directories and tree-wide constraints and then accept the original function from the public entry point. The directory grouping keeps the number of direct files within 15 or more of the directories to which the number rule applies, and over 15 direct sub-directories are reviewed on duty. The root levels `datasets/` and `models/` and their offspring receive them by component and path, exempting them from quantity checks.

When you look at the new features along the public entry point, you first find the data, models and tasks from the formulation and then confirm the processing and preservation of the results along the normal command. For example, when you add an optional new model, you keep the same tasks and indicators, and then you add to the model catalogue to achieve and configure options, and then confirm access from the precheck and running list. When you need to change the indicator or historical comparability, you organize an inspection and human review along [the example of work on the project](engineering.md). The description provides functional changes, performance comparisons and review examples for comparison with the maintenance of the template.

The timer, bottleneck and candidate report for performance precheck is maintained at tasks/precheck. The classification tasks provide a physical forward and fixed sample view, and the operational layer saves the receipt and official results of the prechecking.

The template defaults to load conf/config.yaml from the root of the item and to position the root of the item. The relative data root of the formulation statement starts from the directory where the formula is located, and the visible data path of the command line starts from the command execution directory. When the shared workspace is used, the actual resource path of the shared data/ is transmitted to the same entry.

The grouping is archived on the basis of actual data and models. The location of the extended data analysis task is based on the actual input, and the unused model layer is saved. The extended batch is still archived on its own input and the actual schedule entry is maintained. Repetitible engineering checks are detected and executed by the project test entry.
