# Uninstall EverResearch from one project

## Purpose and main function

Remove the selected project's EverResearch connection and its exclusive local installation files. Verify that the project is disconnected and that unrelated projects can still use their resources.

## Scope of application

Use for authorized removal of an online, offline, or legacy project installation, including disposal of files created solely for an approved trial. Resolve the exact checkout and registration. A separate copy, rollback archive, shared runtime, user work, or a remote repository has its own ownership and authorization.

## Inventory before changing files

Use the caller's explicit template choice for an authorized trial teardown. **Add to templates** means prepare and verify the template before removing the working copy. **Do not add to templates** means remove the trial without creating or replacing a template. An existing approved template stays in place unless the user explicitly requests its removal or update. For an uninstall with no template choice, use the ordinary uninstall scope.

Keep the workspace data root `data/` in place during project uninstall and trial cleanup, including project-named subdirectories and downloaded weights stored there. Remove the project's binding to the data. Leaving the data in place satisfies the uninstall requirement. Deleting workspace data requires a separate request that identifies the data.

An accepted template is the handoff when the user selects template delivery. Follow the [template acceptance standard](../../maintain-skill/references/template-acceptance.md) for the original ZIP, origin and layout documentation, portable files, and verification. Record the checks actually passed and any unresolved runtime coverage, including when the user accepts bounded evidence for delivery. Keep results in the template when they help someone run, reproduce, or check a documented workflow. For either template choice, remove project-only checkouts, environments, caches, test logs, setup backups, recovery packs, and unneeded historical runs outside the template and workspace `data/`. Keep unrelated user work and shared resources. Use the actual producers and ownership evidence to resolve paths before deleting them.

Finish the trial by removing its local goal evidence, including Markdown summaries, manifests, inventories, checksums, source archives, work links, and evaluator scratch files. Include project entries inside a shared batch goal, catalog of trial sources, or evidence file. Remove the finished project's entries while preserving entries for trials that still need the file. Keep the deletion inventory in session memory for reporting, then remove its on-disk copy. A completed skip has no project-specific handoff files outside workspace `data/`. An existing approved template remains available.

1. Resolve the user-selected path and identifier. Use `rh projects list`, `rh projects project status <path>`, and, for a registered project, `rh projects resources <id>`. Compare canonical paths and read the active mode, connection file, setup backup manifest, local installation receipts, and available setup records. Record whether the project is a normal checkout or a disposable trial and whether its removal was requested. Check for live processes writing to any candidate path.
2. Inspect the locations below when they exist. Follow recorded producers, configuration paths, and other bindings to establish who owns each candidate. Folder spelling is a search hint. Resolve paths for comparison, including references from other registered projects, but treat a symlink as a link when removing it.
3. Record the removal candidates and retained resources with their exact paths and ownership evidence in a manifest outside the checkout. A normal uninstall covers proved project-only installation and disposable output. Keep the source tree, reusable assets, raw research data, and research results unless their removal is explicitly authorized and their scope is established. Authorized trial cleanup can include its exclusive staging copies outside workspace `data/`, generated experiment outputs, and checkout. Keep any backup or record needed to recover user work.

| Where to check | What establishes ownership |
| --- | --- |
| Project `AGENTS.md`, `.gitignore`, `.everresearch/`, `.researchharness/`, and client skill directories such as `.agents/skills/`, `.claude/skills/`, or `.cursor/skills/` | Managed markers, exact ignore entries, setup files, and installation receipts. Preserve user-owned sections, local skill edits, and mixed directories. |
| Checkout `.venv/`, `venv/`, or `env/`, and workspace `envs/<project>/` or `envs/<trial>/` | Bound interpreter, `pyvenv.cfg` or environment metadata, creation records, and checks for other consumers. A shared interpreter's symlink target is outside the removal. |
| Checkout `tmp/`, `build/`, `dist/`, `.build/`, `__pycache__/`, `.pytest_cache/`, `.ruff_cache/`, `.mypy_cache/`, and generated package metadata | Build and validation commands, output manifests, and the contents of each directory. Remove entries made solely for this installation or trial. |
| Project-local asset and experiment folders, download and model caches outside workspace `data/`, system temporary folders, and maintenance logs | Recorded acquisition, command output paths, dedicated directories, and active bindings. Remove private caches and disposable outputs of established ownership. Keep shared downloads and irreplaceable data. |
| Central project registry, per-project resources and settings, generated guide and connection, and per-project setup, maintenance, installation, or structure records | Exact registered identifier, path, and matching file contents. Keep user notes and published or reusable records. Leave mixed logs and other projects' entries in place. |

## Remove the selected installation

1. When the user wants original files restored, read the initial setup archive manifest and recover the selected files before removing the backup. Use the manifest to distinguish backed-up files from inventory-only data. Preserve later edits and report any conflict. To clean the project instructions, remove matching managed marker pairs for either prefix and only the setup-created ignore entries. For skills installed by `rh skills install`, use `rh skills uninstall --project <path> --dry-run` with the applicable host options, then apply the same command after checking the plan. Keep user-owned files in either maintenance directory.
2. For an online project, remove its registration and exclusive connection state before removing the resources it points to. Use the supported unregistration command when available. In the source checkout without one, use the central workspace's existing atomic JSON write and lock helpers to remove only the matching identifier from `.workspace/harness/core/central/project_roots.json`. Recheck the registered path under the lock and preserve every other entry. Remove that identifier's resource binding and generated settings, guide, and connection records using the inventory. The owning functions are `HarnessContext.project_record`, `resources.binding_path`, `manage.state_path`, and `manage.online_guide`. Preserve locally authored files in `src/project/maintained/<id>/` and shared or actively held locks. Installed runtimes keep mutable files in their state directory. Offline projects may have no central records.
3. Remove the proved project-only environments, local files, caches, and disposable trial outputs. If ownership remains ambiguous or a process still uses a file, keep it and report the exact path and missing evidence. Use the already-authorized scope to complete the remaining independent removals.

## Verify removal

- For a retained checkout, run `rh projects project status <path>` and require `unmanaged`. For an authorized deleted checkout, verify the path is absent. Verify the exact registration no longer appears in `rh projects list`, and the identified central connection records and binding files are absent.
- For a disposable trial, search for owned leftovers across workspace checkouts, environments, temporary workspaces, sample caches, evaluator copies, and goal or backup folders. Derive search aliases from commands, archive names, package metadata, and logs. Check abbreviated prefixes and probe filenames such as model or dataset metadata JSON in system temporary directories. Use content or producer evidence to establish ownership. Verify the template choice and absence of trial-only files outside the approved template and workspace `data/`. Do not treat moving a trial artifact to another local folder as completion.
- Recheck each inventoried removal path and relevant parent directory. Verify that retained source, backup, and shared data still exist, that other registrations and bindings match the baseline, and that any deliberately retained files have their reason recorded.
- Check retained setup instructions and local links that pointed into removed locations. Update installation-only commands to use the project's documented setup. Mark removed trial outputs as historical and keep factual records intact. Leave unrelated user documentation in place.
- Report the outcome in terms of the project's checkout, installation files, and registration. Include remaining paths only when they prevent completion or need a user decision. Keep routine registration and lock checks in the detailed record.
