# GitHub Publish — 把选定内容发布到 GitHub

## 目的和主要功能

帮助用户把整个项目、某个目录或几个文件发布到 GitHub。先扫描实际目录，说明内容和规模，询问并确定纳入范围，再把选定文件复制到本技能内，准备可查看的变化，并按用户授权完成发布。

提供对照检查模式：先确定每个管理项目的本地路径、GitHub 位置与比较范围，再说明两边的文件和内容差异，供用户决定是否对齐。

提供长期项目管理方式：将用户选定的 GitHub 仓库下载到 `projects/<项目名>/repo/`，在固定项目目录中维护当前副本和远程对应关系。

原发布对象始终保持只读：文件内容和文件集合保持原样。Git 仓库、发布说明、版本包、临时文件和日志都在本技能内准备，实际上传来自内部副本。

## 适用范围

用户要求将选定内容发布或更新到 GitHub 仓库、通过合并请求（PR）提交变化，或制作和发布版本（Release）时使用。用户只要求讨论方案或查看待发布变化时，按该范围准备。

用户要求对照 GitHub 管理的项目与本地技能、查看两边差异或讨论是否对齐时，使用对照检查模式。

用户要求将 GitHub 仓库下载到本地并持续维护时，使用下文的长期项目管理方式。

支持 GitHub.com。运行使用 Python 3.11 及以上版本、Git 和 GitHub 命令行入口 `gh`；仓库发布需要已有的 GitHub 登录或环境中的凭据。所需工作说明与程序均在此文件夹内。待发布项目是读取对象，GitHub 是用户指定的发布目标。

## 发布说明的写法

README、差异说明和发布说明直接解释选定内容提供什么功能、怎样使用以及必要条件。使用常见词语、完整自然语言和肯定句，按读者需要展开技术细节。向用户说明实际变化、影响与需要决定的事项；操作记录保存检查依据，发布交付提供对应的真实链接。

## 选择本次工作方式

发布模式按下文准备副本、展示变化并执行获准发布。对照检查模式先按下文“建立仓库前”完成本地扫描与范围选择，再读取两边资料并报告差异。沿用用户已经选定的模式；同一任务涉及多个项目时，分别确定各项目的对象与范围。

## 长期项目管理

每个长期维护对象使用固定的 `projects/<项目名>/`，名称表达实际用途。`repo/` 保存当前 Git 工作副本，旁边的 `project.md` 说明用途、维护范围、仓库地址、分支、初次取得的提交、本地入口和资料来源。项目清单及阅读入口保存在 `projects/README.md`；每次下载或更新产物在对应项目的 `log_updates.jsonl` 记录。

首次下载前，读取远程文件清单，说明规模、主要内容和影响范围选择的文件，沿用用户在扫描后确认的范围。完整下载采用当前默认分支的浅克隆，保留当前全部受版本管理的内容、可执行属性和符号链接；完整历史、子模块内容和 Git LFS 实体按用户实际需要安排。符号链接保持原样，并按实际目标解释用途。

后续维护先读取项目说明和当前 Git 状态，承接已有的本地改动与用户授权，再决定获取远程内容、比较或修改。本技能内部的长期工作副本按用户的维护授权修改；外部来源目录继续保持只读。发布时从长期工作副本准备本次独立的 `results/<任务标识>/source/` 与 `checkout/`，沿用发布流程展示具体变化并执行获准操作。

固定项目目录保存持续维护的对象；`results/<任务标识>/` 保存各次扫描、比较、发布、临时文件和执行记录。下载和本地登记完成后交付固定项目入口；远程写入依据相应发布任务的授权执行。

## 对照检查模式

### 明确项目路径与范围

每个要管理的项目都明确以下信息，已有记录供本次选择参考，实际操作采用当前确认的对象：

- 本地项目或技能的完整绝对路径，以及本次比较的目录和文件。原始技能、发布副本和其他安装副本分别以实际路径标明。
- GitHub 仓库地址、分支或版本，以及仓库中的对应目录。分支采用用户选择；用户只提供仓库时，使用仓库当前默认分支并说明实际选择。
- 本地与 GitHub 的路径对应关系，例如本地技能目录对应仓库根目录。
- 纳入和略过的内容，例如是否比较 `results/`、缓存、历史资料，以及只在发布副本中增加的 README 和许可证。沿用用户已明确给出的取舍。

先读取已有任务记录和当前目录，找到真实路径与现有对应关系，再集中询问影响比较的缺失信息。用户要求加载技能或准备管理项目时，先明确路径与范围；需要了解两边是否一致时再进入比较。

### 比较并说明差异

将本次选定的本地文件复制到技能内部，并在同一任务内读取 GitHub 的指定版本。记录本地来源、范围、路径对应关系和实际远程提交，使结果对应本次读取的内容。比较过程保留两边原始内容。

按路径对应关系比较两边选定范围内的全部文件，说明本地独有、GitHub 独有、内容不同的文件，以及影响使用的可执行属性变化。文本差异结合实际内容解释具体含义，二进制资料说明文件与内容是否相同。发布时有意增加、翻译或略过的内容，按已有依据说明用途；原因待确认时标明待确认。

现有 `prepare` 用于准备发布变化。对照模式另行比较两边的文件清单，覆盖 GitHub 独有文件。具体操作见下文引用的“准备、发布与保存”。

### 请用户考虑是否对齐

先简短说明整体是否一致，再列出实际差异及其影响，请用户考虑保留各自版本、以本地为准更新 GitHub、以 GitHub 为准调整本地，或只对齐选定内容。建议结合各文件的实际用途说明。

对齐决定应明确方向、涉及的文件和预期结果。用户作出决定后，按选定方向准备具体修改，并依据对应操作的授权实施；原目录沿用本技能的只读规则，本地调整先准备内部副本与具体差异，原目录的实际修改通过目标项目的维护流程处理。当前任务只要求比较时，以差异说明和待选择事项结束。

## 建立仓库前：扫描、说明和选择范围

本节沿用 ExtractStructure 的“先查看实际对象，再说明规模与用途，最后选择范围”的工作顺序，按发布需要统计所有文件类型。这里完整保存本技能需要的步骤，运行时直接按本节执行。

适用于建立临时本地仓库、准备发布副本、制作版本包和向 GitHub 发布。扫描与范围选择发生在复制文件、初始化 Git 仓库、暂存和提交之前。

### 1. 扫描用户指定的对象

用户已经指定项目、目录或文件时，扫描该对象；尚未指定时，轻量查看当前目录、已有说明和少量代表性内容，推荐约三个实际入口。每个入口给出完整路径和一句用途说明，等待用户选择。

对选定对象进行只读目录扫描，统计文件数、总大小、主要文件类型和主要目录。结合已有说明和必要的少量阅读，解释各主要目录的实际用途。用途待确认时明确写出“用途待确认”。扫描覆盖隐藏目录，并分别列出：

- 程序、配置、使用说明和开发资料。
- 历史资料、备份、生成结果、日志、缓存和临时文件。
- 本机配置、较大的文件或压缩包，以及可能影响 GitHub 发布的文件。
- 已有 Git 元数据、符号链接，以及本技能内已有的发布副本。

每个主要目录采用“完整路径 — 实际用途；文件数和大小”的表达。已有排除要求单独列明；用户提供的目录名称与实际名称有差异时，说明实际对应关系。扫描保持轻量，文件清单与必要阅读用于范围选择。

### 2. 展示扫描结果并询问范围

先用一两句话说明项目的主要内容和总体规模，再展示影响选择的目录、历史资料、结果和大文件。根据实际内容推荐范围，提供以下可调整的选择：

1. **程序和使用说明（推荐）**：明确列出纳入的源码、配置、文档，以及建议略过的具体目录。
2. **全部内容**：包含扫描发现的历史资料、结果、日志、缓存和本机资料；明确写出仍会略过的 Git 元数据与本次生成目录。
3. **自选范围**：让用户指定需要带上的目录或结果，并给出一个符合实际项目的简短示例。

推荐项按用户目的调整。例如，完整本地备份可推荐全部内容，程序对外发布可推荐程序和使用说明。只建立临时本地仓库时，也执行上述扫描与询问。

用户笼统要求“整个项目”或“除了某目录以外全部内容”时，先按该要求列出候选范围，再结合实际发现询问一次。得到本轮扫描说明之后的范围选择，再开始复制和建立仓库。用户已经在本轮扫描后确认范围时，沿用该决定；已有回答只对新增或发生变化的范围补充询问。

### 3. 记录选择，再准备内部副本

简短复述来源完整路径、纳入内容、略过路径和预计规模。将选择保存到本任务的范围记录，并落实到复制使用的映射和排除项。扫描记录、范围选择和后续副本均保存在本技能内。

程序会略过 Git 自身资料，并在选择父目录时略过本技能的运行产物，防止把正在生成的副本再次复制进去。用户选择纳入已有发布产物时，明确记录具体已有路径，并采用独立复制方式纳入；本次生成目录始终排除自身。

完成范围确认后，按下文准备内部副本和本地仓库。目标仓库、公开范围和远程发布行为在实际需要时确定；只建立本地仓库时，沿用本地操作范围。

需要 Release 时，同时讲清仓库内容与下载附件是否采用相同范围。GitHub 自带的源码下载取自版本标签对应的整个仓库，上传的版本包附件可只包含选定文件。若用户要求排除已存在于目标仓库中的资料，先说明仅缩小附件范围仍会保留仓库中的文件，再确认是否调整仓库发布范围。所有范围调整均作用于内部副本，原对象保持原样。

## 确定发布到哪里

从当前任务和用户已提供的信息中确定以下事项，缺少实际必需的信息时集中询问：

- 目标仓库，是已有仓库还是新仓库；新仓库明确公开或私有。
- 文件放在仓库根目录，还是某个子目录；多个来源可以分别指定位置。
- 直接更新指定分支，还是提交 PR。
- 本次只发布内容，还是还需要带版本号和下载包的 Release。

例如，`ExtractStructure/` 的内容可以成为独立仓库的根内容，也可以放到已有仓库的 `skills/extract-structure/` 下。

默认发布当前选定内容的副本。保留原项目的提交记录、持续自动同步或部署网站属于不同需求，用户明确提出时再确定做法。

## 发布语言与翻译

本次上传的文件路径、正文、代码注释、界面文案和 GitHub 发布说明使用英文。项目已有或用户明确要求提供的中英双语功能，按实际语言版本保留必要的中文文件、语言切换入口和资源。英文项目使用英文 `README.md`。双语项目沿用现有两种语言的文件名与切换方式，核对两种版本的用法、命令和必要条件。

有 GitHub 目标的准备操作自动检查选定文件的目标路径和可解码文本，发现双语范围之外的汉字时记录路径和行号并暂停。根据检查结果翻译技能内部副本，再准备并复查差异。发布与打包会复查准备内容，提交说明、合并请求和版本说明另行检查。评阅其他语言的文字以及图片、文档附件或编码内容中的可见文字时，依据实际发布内容判断。

翻译采用自然、准确的英文。先理解句子的用途，再用读者熟悉的词和常见搭配表达。领域术语沿用项目已有定名或通行表达，保留必要的技术含义，避开生硬直译、自造术语和牵强的复合词。译后对照原文复核含义、条件和操作步骤，再通读英文检查表达是否自然。保持命令、代码标识、数据格式和字段语义准确。遇到中文机器标识或程序依赖的路径时，先查清调用关系，再在本次授权范围内协调改名或调整发布范围。

发布前按仓库查阅[翻译备忘录](references/translation-memo.md)，记录以后会复用的译法和已确认的双语范围。该文档保存各项目的惯用英文、双语入口和重要翻译决定，适用于技能内部的翻译准备与复查。准备时根据本次选入的文件声明对应双语路径。

## 准备内部副本并说明变化

1. 将选定文件实际复制到 `results/<任务标识>/source/`，保留内容和可执行属性。使用独立文件；目标项目的目录保持原样。
2. 在同一任务的 `checkout/` 准备目标仓库，把内部副本放到选定位置。首次发布可先在本地准备空仓库，创建 GitHub 仓库留到实际发布时执行。
3. 默认只新增和更新选定路径。删除目标仓库中的文件时，明确列出待删除路径及用户的对应授权。
4. 按发布语言要求翻译和复查，保存实际差异，向用户说明将新增或修改的内容。复制所需依赖、补充其他文档、许可证或调整版本号等操作按本次授权在内部副本中处理，再重新准备差异。

源文件夹中保持原样的内容包括 `.git`、README、许可证、版本号、打包文件和运行结果；发布所需的新增文件全部位于技能内。构建命令和其他可能写文件的操作使用内部副本作为工作目录，输出、临时文件和缓存也指定在内部。

需要调用程序或准备对照检查时，阅读[准备、发布与保存](references/commands.md)。该文档的目的和主要功能：说明发布程序的命令、文件范围、内部副本、差异和结果保存方式。同时说明如何在技能内部准备本地与 GitHub 的比较副本，覆盖两边文件集合并记录差异。适用范围：执行目录或文件复制、仓库发布、合并请求（PR）、版本包或版本发布（Release）操作时使用。此文档供智能助手调用内部程序，对用户的交流沿用 SKILL.md 中的功能语言。对照 GitHub 项目与本地技能、准备比较副本和查看差异时，同样使用本文件。

## 按已确认范围发布

展示变化后，沿用用户已经明确给出的发布授权。只有目标、公开范围、删除内容或发布行为尚未获得授权时，才补充询问缺少的决定。准备工作完成后再请求实际发布的批准，使用户能看到具体结果。

实际发布只使用已准备的内容。内部副本、待提交内容或远程分支发生变化时，说明变化并重新准备；本次已展示的内容和发布授权相互对应。

发布失败时记录实际完成到哪一步，保留内部副本。先查看本地结果与远程状态，再决定沿用已有资源、重新准备或继续创建。程序使用普通推送，远程冲突保留给下一次明确处理。

建立 PR 后，如当前宿主提供 PR 附件工具，将真实 PR 链接附到当前任务。此能力只用于交付链接，技能的准备和发布流程使用自带程序即可完成。

## 交付与保存

完成后返回真实的提交、PR 或 Release 链接，用一两句话说明发布了什么。只制作本地版本包时，返回内部文件的完整路径。发生部分失败时，分别报告已完成和待处理的操作。

长期项目的当前工作副本和对应关系保存在本技能的 `projects/<项目名>/`，每次操作的准备资料与记录保存在 `results/<任务标识>/`。任务记录说明来源、文件放置位置、实际差异和已完成结果；登录凭据只在当前进程中使用。

测试、浏览器验证和额外源码修改按用户明确要求处理。每次外部写入均以用户对具体发布任务的授权为依据。
