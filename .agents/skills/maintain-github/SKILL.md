# Maintain GitHub — 把选定内容发布到 GitHub

## 目的和主要功能

帮助用户更新 GitHub 仓库或正式发布版本。先确定本次走日常更新还是正式发布，再把选定文件复制到本技能内，准备可查看的变化，按对应流程完成交付。

提供对照检查模式：先确定每个管理项目的本地路径、GitHub 位置与比较范围，再说明两边的文件和内容差异，供用户决定是否对齐。

原发布对象始终保持只读：文件内容和文件集合保持原样。Git 仓库、发布说明、版本包、临时文件和日志都在本技能内准备，实际上传来自内部副本。

## 适用范围

用户要求将选定内容发布或更新到 GitHub 仓库、通过合并请求（PR）提交变化，或制作和发布版本（Release）时使用。用户只要求讨论方案或查看待发布变化时，按该范围准备。

用户要求对照 GitHub 管理的项目与本地技能、查看两边差异或讨论是否对齐时，使用对照检查模式。

支持 GitHub.com。运行使用 Python 3.11 及以上版本、Git 和 GitHub 命令行入口 `gh`；仓库发布需要已有的 GitHub 登录或环境中的凭据。所需工作说明与程序均在此文件夹内。待发布项目是读取对象，GitHub 是用户指定的发布目标。

## 先决定本次走哪条路

| 用户的任务 | 采用的流程 |
| --- | --- |
| 只查看差异或讨论如何对齐 | [对照检查](#对照检查模式)。准备并报告所需信息。 |
| 更新、同步、提交、推送或开 PR | [日常更新](#日常更新)。这是发布类任务的默认流程。 |
| 明确要求为指定版本制作正式发行 | [正式发布](#正式发布)。准备完整方案，取得本次发行的人工批准后执行。 |

同一任务涉及多个仓库时，分别按[更新范围和比较基线](#更新范围和比较基线)确定本次文件范围，再确定目标分支和更新方式。统一说明需要人工批准的操作及其影响。
用户只要求准备日常更新或正式发布方案时，走对应流程的准备步骤，交付差异或方案供审阅。

遇到模板或插件的 Git LFS 问题、更新遗漏、正式发布或回退时，读[GitHub 维护经验](references/field-notes.md)的对应条目。该文档分类记录实际问题、处理步骤和验收证据，适用于仓库更新、模板迁移、插件同步和版本发布。

## 日常更新

**日常更新只交付源码和文档等仓库改动。禁止修改发行版本号、创建或推送版本标签、创建 GitHub Release，或向 PyPI、npm 和插件市场发布新版本。** 推送或合并前检查版本字段和自动发布条件。若当前差异会触发发版，先在内部副本排除该变化，或者等待用户启动正式发布流程。

涉及版本、安装说明或插件技能副本时，按[源码、插件副本和发行版本核对清单](references/installer-artifacts.md#源码插件副本和发行版本核对清单)逐项检查。正式发布也使用同一份清单。

- **持续维护的仓库，例如 EverResearch。** 将每次有明确目的的更新提交为 PR。同一项改动继续更新原有 PR，以指向 `main` 且仍待合并的独立 PR 计数。累计至少 10 个后，整理本批范围、合并顺序和整体影响，提交人工审核。批准后把该批 PR 合并到 `main`。达到 10 个 PR 触发批次审核。有实质性改进时，可以另行提出正式发版建议。
- 对持续维护的仓库，用户说「push to main」或「推送到主分支」时，默认以 `main` 为 PR 的合并目标。先创建或更新 PR。未满 10 个待合并 PR 时，交付本次 PR 并等候后续批次。只有用户明确要求本次跳过 PR、直接推送，并在看到实际差异后批准，才直接写入 `main`。
- **普通科研项目。** 准备一次直接推送到 `main` 的更新，按下文提交一次人工审核。获批后直接推送。用户指定 PR 或其他分支时，按指定方式准备。进入 `main` 的审批要求同样适用。

## 正式发布

用户明确指定本次正式发布及版本后，确认上一个已发行版本、候选版本、目标提交、版本标签和所有分发渠道。按本节和[人工审核](#人工审核)准备完整方案。取得对该方案的明确批准后，执行其中列明的发版操作。

EverResearch 正式发布时还需读取本机的 `results/everresearch-downstream.md`，核对下游项目、CLI、插件、包仓库及安装入口。清单和执行记录保存在本机忽略目录。涉及构建或者迁移安装文件时，读[安装产物与下载入口](references/installer-artifacts.md)，其中包含版本占用、安装地址和校验的要求。

### EverResearch 正式发布的同步范围

1. 用获准的版本号和同一个源代码提交构建 CLI 和插件。核对版本字段、安装入口、每份插件锁定的 wheel 和 SHA-256。先在隔离环境中安装候选包，验证项目接入、项目 Python 与维护运行时分离，以及公开命令。
2. 发布后，从公开地址重新下载 CLI 和可用的插件包，核对公开 wheel 的 SHA-256 与插件锁定值。等安装文件可下载后，再更新依赖这些文件的市场清单和安装入口。逐个核对仓库分支、版本标签与安装说明所指的实际版本。
3. 逐个更新已登记的下游项目，按批准的范围执行仓库更新或版本发布。用空环境从公开入口安装下游项目，连接到本次公开 CLI，再验证帮助、项目维护和受影响的公开命令。记录上游和下游的提交、版本、安装来源及验证结果。
4. 将 GitHub 源码发布、Release 下载、包仓库安装和各市场审核记录为各自可核实的状态。遇到账号权限或平台审核时，完成其他已授权渠道并说明实际尝试、具体阻碍和可继续的动作。本机项目清单、凭据、测试副本和实验结果留在已忽略的工作目录。

## 人工审核

**直接推送到 `main`、把 PR 合并到 `main`、正式发布，以及其他会重大影响仓库的操作，都必须先展示实际差异和操作说明，再等人类明确批准。** 用户授权更新仓库，可以据此准备差异和开 PR。进入主分支和实际发版各有独立的批准范围，同一份明确批准可以覆盖说明中列出的多个操作。新增操作或实质性修改范围后，更新说明并重新审核。普通科研项目直接推送时，一次说明和一次批准即可。

按根目录 `AGENTS.md` 的汇报规则，用人类能理解的语言写说明。先讲这批改动解决什么问题、会影响谁，再给出可核对的证据：

- **更新 `main`。** 列出仓库、分支、待推送提交或待合并 PR、改动范围与完整的变更文件清单。写清每个文件或一组相关文件改了什么、为什么改。说明验证结果，以及合并或推送是否会触发部署或其他自动操作。附上实际差异。
- **正式发布。** 包含上述改动说明，另列版本、标签、候选提交、附件、公开渠道、安装入口和需要一同发布的插件及下游项目。逐项说明涉及的仓库、是否也要发新版本、兼容性、发布顺序和验证结果。说明发布后如何验证公开安装。
- **有无法完成或未达标的部分。** 写清差距、核心原因、已做尝试、影响和下一步。说明当前卡在待判断的方案、待人类决定的事项，还是外部环境和权限。

先交付审核说明，再执行获批操作。未获批时，保留已准备好的差异或 PR，并说明目前在等哪项决定。

## 必须遵守的书写与交流规则

以下原文复制自 EverResearch 根目录 AGENTS.md 的“书写、解释与对话原则”，作为本技能内必须遵守的规则。使用本技能起草、修改或翻译 README、其他 Markdown、合并请求说明和版本说明，以及向人类解释和汇报时，均遵循这些原则。英文和中文采用相同的表达要求。

### 7. 书写、解释与对话原则

本原则适用于书写文件、向人类解释问题和与人类沟通，目的是确保人类能够理解所写、所说的内容。

1. **使用常见词语。** 将代号、生造合成词和需要专业背景才能理解的词语，改为常见、直白的表达，直接说明具体对象、作用和结果。
2. **使用完整的自然语言。** 缩写和代码表达统一改为完整词语与人类可以直接理解的说明。
3. **用肯定句说明概念与关联。** 直接说明每个概念的含义、作用、相互关系及适用情形，概念区分与边界说明一律采用肯定句式。
4. **按人类需要提供细节。** 日常书写和交流以理解实际问题、用途和结果为主；技术细节与执行边界在人类明确要求时再展开。默认将执行边界的模糊之处和技术细节的描述缺失视为对任务影响轻微的情况，按现有信息继续处理。

## 对照检查模式

### 明确项目路径与范围

每个要管理的项目都明确以下信息，已有记录供本次选择参考，实际操作采用当前确认的对象：

- 本地项目或技能的完整绝对路径，以及本次比较的目录和文件。原始技能、发布副本和其他安装副本分别以实际路径标明。
- GitHub 仓库地址、分支或版本，以及仓库中的对应目录。分支采用用户选择；用户只提供仓库时，使用仓库当前默认分支并说明实际选择。
- 本地与 GitHub 的路径对应关系，例如本地技能目录对应仓库根目录。
- 纳入和略过的内容，例如是否比较 `results/`、缓存、历史资料，以及只在发布副本中增加的 README 和许可证。沿用用户已明确给出的取舍。

先读取已有任务记录和当前目录，找到真实路径与现有对应关系，再集中询问影响比较的缺失信息。用户要求加载技能或准备管理项目时，先明确路径与范围；需要了解两边是否一致时再进入比较。

### 比较并说明差异

将本次选定的本地文件复制到技能内部，并在同一任务内读取 GitHub 的指定版本。记录本地来源、范围、路径对应关系和实际远程提交，使结果对应本次读取的内容。比较过程保留两边原始内容。

按路径对应关系比较两边选定范围内的全部文件，说明本地独有、GitHub 独有、内容不同的文件，以及影响使用的可执行属性变化。文本差异结合实际内容解释具体含义，二进制资料说明文件与内容是否相同。发布时有意增加、翻译或略过的内容，按已有依据说明用途；原因待确认时标明待确认。

现有 `prepare` 用于准备发布变化。对照模式另行比较两边的文件清单，覆盖 GitHub 独有文件。具体操作见下文引用的“准备、发布与保存”。

### 请用户考虑是否对齐

先简短说明整体是否一致，再列出实际差异及其影响，请用户考虑保留各自版本、以本地为准更新 GitHub、以 GitHub 为准调整本地，或只对齐选定内容。建议结合各文件的实际用途说明。

对齐决定应明确方向、涉及的文件和预期结果。用户作出决定后，按选定方向准备具体修改，并依据对应操作的授权实施；原目录沿用本技能的只读规则，本地调整先准备内部副本与具体差异，原目录的实际修改通过目标项目的维护流程处理。当前任务只要求比较时，以差异说明和待选择事项结束。

## 更新范围和比较基线

### 默认更新整个项目

用户要求更新项目、开 PR、推送或同步时，以项目根目录为文件来源。**默认对照整个项目，纳入所有未被 Git 忽略的项目文件变化。** 包括已跟踪文件的修改，以及新增的未忽略文件或目录，例如模板、测试、资源和配套文档。按实际差异确定范围，避免把最近讨论过的文件当成本次的完整清单。没有变化的文件无需重新提交。

用户明确只更新某个组件、目录或文件时，按指定范围操作。**此默认方式可以按项目调整。** 项目已有用户确认的发布范围时沿用，并在任务记录中写清范围和依据。项目尚不明确时，只确认要更新哪个项目。

把来源中已经存在的改动原样复制到审阅分支，属于准备项目更新。项目对助手新改源码、布局或参数的限制适用于新编辑。只有明确限制提交或公开某些文件的规则，才据以从更新范围排除对应文件，并在报告里写清依据。发现已有改动可能影响项目行为时，把影响写进差异说明，保留在审阅范围内。

### 与上一次实际更新比较

1. 查找同一项目上一次实际传到 GitHub 的更新。候选包括仍在使用的 PR、主分支上的更新和已发布版本。按实际推送、合并或发布时间排序，选择最近一次适用的更新。PR 使用其最近一次代码提交所对应的更新时间，版本使用发布时间。评论、标签编辑和本地文件修改时间不参与排序。首次更新且目标为空时，以空文件清单为基线。
2. 记录选中记录的类型、链接、时间戳和准确提交。沿用已有 PR 时，对照它当前的提交计算本次新增差异。准备向主分支提交时，再用实际目标分支检查完整差异，确保此前未合入的改动不会遗漏，也不会覆盖目标分支的新变化。用户指定比较基线时使用指定基线。
3. 对照范围内的文件清单和实际内容，列出新增、修改和待删除路径。只在远端存在的文件先查明来源和用途。已有文件的删除按明确授权执行，先在报告中列清具体路径。

### 用 Git 忽略规则落实范围

使用项目实际生效的 Git 忽略规则生成清单，包括根目录和嵌套目录的规则。被忽略的结果、本机配置、缓存和临时文件留在本地。已被远端跟踪但现在命中忽略规则的文件，记录现状并按授权处理删除。扫描忽略规则时，可依据文件用途建议调整规则。当前更新以生效规则和已确认范围为准。

审查 EverResearch 的忽略规则时，对 `.agents/skills/` 和 `src/` 采用同一原则。共享方法、代码、通用模板、测试和可复用样例应纳入。具体项目的本机绑定、运行结果、发布副本和会话记录应排除。把审查建议与本次更新清单分别记录，规则调整按授权执行。

`prepare` 按传入的映射和排除参数复制文件，并用 `git add -f` 暂存。按[准备文件范围](references/commands.md#准备文件范围)把实际文件清单传给它，再核对 `plan.json` 和待提交差异，确认清单中的变更全部进入本次更新。

正式发布时，另行说明仓库与附件的范围。GitHub 的源码下载取自标签对应的整个仓库，上传附件可以按用户指定范围准备。

## 确定发布到哪里

从当前任务和用户已提供的信息中确定以下事项，缺少实际必需的信息时集中询问：

- 目标仓库，是已有仓库还是新仓库；新仓库明确公开或私有。
- 文件放在仓库根目录，还是某个子目录；多个来源可以分别指定位置。
- 按日常更新或正式发布的流程确定 PR、推送和发布目标。目标仓库没有 `main` 时，确认实际承担主分支职责的分支，并对进入该分支的改动执行同样的人工审核。

例如，`ExtractStructure/` 的内容可以成为独立仓库的根内容，也可以放到已有仓库的 `skills/extract-structure/` 下。

用本次范围内的独立副本更新目标仓库。保留原项目的提交记录、持续自动同步或部署网站属于不同需求，用户明确提出时再确定做法。

## 发布文档的默认语言

一般默认以英文发布面向读者的 Markdown，用户明确指定语言时沿用该选择。与用户交流继续使用用户选择的语言。

发布内容的说明入口默认采用英文 `README.md`，同时提供内容对应的中文说明 `README.zh-CN.md`。两份文件的开头、正文介绍之前都放置语言切换链接，让读者可以直接选择英文或中文：

```markdown
[English](README.md) | [中文](README.zh-CN.md)
```

两种语言说明相同的用途、使用方式和必要条件，命令、路径和字段保持准确对应。其他面向读者的 Markdown 默认使用英文。已有文档采用其他中英文文件名时，沿用现有组织方式，使用实际相对路径连接两个版本；用户明确要求不同语言安排时按其要求处理。

起草、翻译、补充中文说明和添加切换链接均在本技能的发布副本内完成，原发布对象保持原样。准备差异时将英文说明、中文说明及其链接一并列入待发布内容；版本包包含本次选定交付的说明文件。源文件中由程序读取的格式、字段和标识保持现行写法，文档解释按上述语言要求整理。

## 准备内部副本并说明变化

1. 将选定文件实际复制到 `results/<任务标识>/source/`，保留内容和可执行属性。使用独立文件；目标项目的目录保持原样。
2. 在同一任务的 `checkout/` 准备目标仓库，把内部副本放到选定位置。首次发布可先在本地准备空仓库，创建 GitHub 仓库留到实际发布时执行。
3. 核对默认全量范围或用户明确限定的文件清单。删除目标仓库中的文件时，明确列出待删除路径及用户的对应授权。
4. 按上述默认语言要求准备发布说明，保存实际差异，用简短说明告诉用户将新增或修改哪些内容、目标仓库其他部分是否受影响。复制所需的依赖、补充其他文档、许可证或调整版本号等，先说明实际需要；获准后只在技能内的副本上处理，再重新准备差异。

源文件夹中保持原样的内容包括 `.git`、README、许可证、版本号、打包文件和运行结果；发布所需的新增文件全部位于技能内。构建命令和其他可能写文件的操作使用内部副本作为工作目录，输出、临时文件和缓存也指定在内部。

需要调用程序或准备对照检查时，阅读[准备、发布与保存](references/commands.md)。该文档的目的和主要功能：说明发布程序的命令、文件范围、内部副本、差异和结果保存方式。同时说明如何在技能内部准备本地与 GitHub 的比较副本，覆盖两边文件集合并记录差异。适用范围：执行目录或文件复制、仓库发布、合并请求（PR）、版本包或版本发布（Release）操作时使用。此文档供智能助手调用内部程序，对用户的交流沿用 SKILL.md 中的功能语言。对照 GitHub 项目与本地技能、准备比较副本和查看差异时，同样使用本文件。

## 按已确认范围发布

按已选流程执行。开日常 PR 时沿用本次仓库更新的授权。更新主分支、正式发布和其他重大操作按[人工审核](#人工审核)执行。目标、公开范围或删除内容尚有缺失时，只补充需要用户决定的事项。

### 部署前核对目标环境

发布会自动触发部署，或本次任务包含手动部署时，在推送或触发部署之前，确认目标仓库、分支、部署流程和目标站点。读取目标分支上的部署配置和依赖版本文件，结合部署平台当前的支持说明，核对实际运行镜像、运行时与构建工具版本，以及项目依赖能否在该环境中安装。部署依赖环境变量或密钥时，只核对配置项是否就绪。

使用 `ubuntu-latest` 等会随平台更新的标签时，确认它当前对应的镜像和项目固定版本是否兼容。例如，学术网站指定 Ruby 3.3.5，`ubuntu-latest` 切换到 Ubuntu 26.04 后，该版本无法安装，网站改用 Ubuntu 24.04 完成部署。发现同类冲突时，先在授权范围内修复并重新核对环境，再执行部署。将确认的环境、发现的问题和修复结果记入本次任务记录。

执行前核对内部副本、待提交内容和远程分支，确保实际操作与已展示并获批的范围一致。发现变化时，重新准备差异，按人工审核规则处理。

发布失败时记录实际完成到哪一步，保留内部副本。先查看本地结果与远程状态，再决定沿用已有资源、重新准备或继续创建。程序使用普通推送，远程冲突保留给下一次明确处理。

建立 PR 后，如当前宿主提供 PR 附件工具，将真实 PR 链接附到当前任务。此能力只用于交付链接，技能的准备和发布流程使用自带程序即可完成。

## 交付与保存

完成后返回真实的提交、PR 或 Release 链接，用一两句话说明发布了什么。只制作本地版本包时，返回内部文件的完整路径。发生部分失败时，分别报告已完成和待处理的操作。

全部本地产物保存在本技能的 `results/<任务标识>/`。任务记录说明发布来源、文件放置位置、实际差异和已完成结果；GitHub CLI 负责认证，任务结果保存提交或发布状态。

测试、浏览器验证和额外源码修改按用户明确要求处理。每次外部写入均以用户对具体发布任务的授权为依据。
