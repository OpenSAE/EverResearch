# 接入并整理科研项目

## 目的和主要功能

把已经存在的科研项目整理成可接手的结构。先找出代码、配置和产物各自在实际运行中做什么，再按职责决定保留、迁移、拆分或适配，并把正常入口接到整理后的实现。

## 适用范围

用户要求挂载、梳理或按 ResearchHarness 模板整理一个新接触的项目时使用。输入为项目目录或仓库、目标工作区及本次整理范围。以当前项目已有行为为依据，从正在使用的流程开始，按本次范围逐条处理。

## 定位项目和现有入口

- **建立或复用父工作区。** 用户要求挂载或初始化时，确定父工作区和其中的 ResearchHarness 源码目录。约定 `ResearchHarness/`、共享 `data/` 和各科研项目仓库为平级一级目录。已有工作区标识时复用。首次初始化时执行 `rh projects --harness-root <ResearchHarness目录> init-workspace`，在它的父目录创建工作区标识和共享数据目录。仅有远程仓库时，将选定项目的工作副本放在工作区的一级目录。项目已有其他实际位置时沿用其位置并登记。
- **登记与传入资源。** 挂载时用 `rh projects register <项目标识> --path <项目目录>`；需要接入共享技能时用 `rh projects apply <项目标识>`。已有共享数据时按用途用 `rh projects bind <项目标识> --data <名称>=<路径>` 登记，再通过项目支持的命令参数或环境变量交给实际入口。仓库内路径由项目根或明确声明的配方位置解析。大型数据、外部权重和本机解释器使用本机选择。
- 确定要读的仓库与要改的工作区，查看项目说明、当前源码版本和已有本地改动。仅有远程地址时，按授权取得工作副本。已经登记的项目沿用现有绑定。需要正式挂载时，通过所选中央 ResearchHarness 的 `src/harness/core/PROJECT.md` 找到本机项目登记以及可选的数据目录和 Python 绑定；需要同步共享技能时，按 `src/harness/projects/README.md` 使用现有接入入口。资料尚未齐全时，源码摸底仍可在工作区内进行。
- 先找一条项目实际使用的命令、工作流或 Notebook。优先读 README 里的运行示例、提交脚本、配置和近期结果的来源记录。若入口互相矛盾，沿它们的实际调用和产物区分当前流程、历史流程和示例；证据不足的入口标为待确认。使用 `extract-structure` 的仓库模式画一张选定范围的结构草图，聚焦入口及主要调用。用原始配置、Notebook、外部库调用和已有结果补上图中看不到的环节。
- 对照所选中央工作区的 `src/harness/projects/LAYOUT.md`、`PROTOCOL.md` 和同目录的 `template/`。布局用于确定职责归属，工程协议用于核对涉及的调用和记录约定，模板用于查看这些职责怎样连起来。按实际需要选择二级目录、登记方式和文件粒度。

## 从混杂代码中提取职责

1. **从入口向下追。** 写下实际入口、传入参数、默认值和覆盖顺序。顺着导入、函数调用、配置标识或框架回调找到真正被调用的实现。入口是 Notebook 时，顺着单元之间传递的配置、数据、模型和结果追踪；工作流有多个阶段时，按每条命令的输入和输出串起来。看到外部框架时，定位项目传给它的配置、组件或回调，以及从框架接回的输出。
2. **从结果往回找。** 在已有日志、指标、预测或检查点里选本次流程真正使用的结果，找出谁算的、谁写的、谁读的。特别留意写入路径和配置是否由启动脚本、环境变量或框架隐式决定。查到文件、函数、配置键或 Notebook 单元就记下位置；找不到的环节记下具体缺项。
3. **按工作内容划分。** 对每个承担实际工作的函数、类、代码块或配置段，回答四件事：谁调用它、它接收什么、它交付什么、谁继续用。以这四项判断归属。一个文件同时做几件事时，按工作内容分别定位；不同入口调用同一实现时，保留一个负责位置。

| 在原项目里看到的实际工作 | 布局中的归属 |
| --- | --- |
| 查找原始输入、读样本、构造标签、划分、采样、样本变换 | `datasets/` 收纳实现。原始数据留在原有数据根或已登记的外部位置。保留原有划分与标签含义。 |
| 声明模型变体、构建网络、执行前向、加载模型专用权重 | `models/` 收纳模型实现或框架适配。用于恢复训练的优化器、轮次等状态随任务或运行流程处理。 |
| 选用数据和模型，训练、评估、推理或分析，计算损失和任务指标 | `tasks/` 收纳任务编排与研究计算。任务依赖组件的公开接口。 |
| 默认值、组件选项和覆盖项 | `conf/` 保存供入口读取的项目默认配置及可选项；单次运行的生效参数随该次实验保存。模型、数据和任务专用参数的含义与检查仍由对应组件负责。 |
| 读命令参数、合成配置、选接数据集与模型、分发任务、管理通用运行资源 | 命令入口负责接收请求，项目级协调与共用能力优先归 `base/`。已有框架或运行包具备清晰的同等职责时，可保留实际位置并指明入口。 |
| 写入或查找运行的日志、指标、报告、预测与检查点 | 新运行的产物归项目根目录 `experiment/`；通用落盘由运行模块负责，指标含义由任务负责。历史结果保留原有位置和读取方式，在项目说明中指明。 |
| 人工启动、批量提交或演示 | 有独立用途时保留在脚本或 Notebook 中，让它调用正式实现。 |

## 按映射整理文件和入口

- 在现有项目说明或本次交接里记一份简短映射，格式为「原位置和调用者 → 实际职责 → 新位置或保留入口 → 如何处理」。已有职责放对位置就保留；职责清楚的实现直接迁移；混杂文件从输入输出清楚的代码块拆出；外部框架、稳定公共接口或暂时紧耦合的实现，通过现有入口或薄适配接到相应职责。适配层应调用真实实现。尚无实现、当前无法拆出或作用待确认的部分，写明原因和当前落点。
- 每次先改同一条调用链上的一组职责。移动或拆分后，沿原调用者更新导入、配置引用、命令或脚本、相对路径基准和说明；已公开的命令与标识通过原入口或兼容转发继续指向同一实现。整理参数时保留原有默认值与覆盖顺序。先把现有工作归位，再按实际复用需要决定是否引入更多子目录或组件登记。专项处理可调用 `maintain-base`、`maintain-dataset`、`maintain-model`、`maintain-task` 和 `maintain-optional`。
- 例如 `train.py` 同时随机划分数据、构造模型、训练并写出准确率。先找到划分所用的种子和索引，把对应逻辑归数据组件；将模型构造和权重加载归模型组件；保留训练循环和准确率计算在任务中；由入口传入参数，由运行模块保存指标。原命令继续转发给整理后的任务。若项目只有一个端到端框架命令，先对应配置、回调和产物的职责，再决定是否需要拆内部代码。

## 接通项目基础层

从正常命令找到合成配置、选择或构造组件、执行任务的实际代码。把跨组件连接、共用运行逻辑和路径解析归到 `base/` 或已有等价位置。先接通一条实际链路。入口传入请求，基础层定位配置、数据根和结果目录，接入数据和模型并调用具体任务，任务完成研究计算。说明项目默认路径和用户输入各从哪里起算，以及外部资源怎样传入。记录结果怎样由后续调用者读取。项目需要按标识组合多个实现时，沿现有选择方式整理登记入口。具体改动可用 `maintain-base`。

## 建立组件文档

强烈推荐在 `doc/` 至少提供 `datasets.md`、`models.md` 和 `tasks.md`，并从 README 导航。已有同用途文档时，沿用其位置并补齐内容。每份用一节集中说明该类组件真实共用的参数，再逐项介绍实际支持的数据集、模型系列或选项、任务和重要模式。每项写清主要功能、正常入口、输入与产物、关键参数及其含义，按需要给出单位、默认值、允许值、覆盖关系或适用条件。共有参数的单项差异写在对应项，参数依据实际读取代码和配方。文档与本次整理同步更新，具体做法可用 `maintain-optional`。

## 交给后续维护

本次完成以约定范围内的职责已明确、能落地的整理已实施、后续维护者能定位入口和责任模块为准。用简短交接写清正常命令、基础层入口、组件说明和历史结果位置，并列出仍待整理的部分。交接结论以实际完成的改动为依据。实验运行、指标对照和性能验证可以后续交给 `maintain-experiment`，按用户指定的范围执行。
