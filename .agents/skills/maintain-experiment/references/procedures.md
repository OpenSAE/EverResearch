# 实验操作方案

## 目的和主要功能

把项目默认配置、单次参数及实验执行、跟踪、恢复和调试落到实际文件和入口。

## 适用范围

用于维护默认配置和单次实验参数、执行获准实验、读取已有结果、恢复已有工作或定位问题。根项目说明登记实际命令、路径、恢复能力与项目例外。实验产物根为项目一级目录 `experiment/`，由项目根推导。各项目可登记其内部层级及等价的结果读取入口。

## 文件归属

| 位置 | 负责内容 |
| --- | --- |
| `main.py`、项目包的 `cli.py` 或 `__main__.py`、`tasks/workflows.py` | 读取命令参数并选择正常操作。实际计算进入对应任务 |
| `conf/config.yaml` 或项目默认入口 | 组织一套默认配置，选择数据、模型、任务、工作量、设备及输入根 |
| 项目包的 `runtime/config.py`、`runner.py`、`environment.py`、`records.py` 或等价模块 | 合成配置、分发任务、采集实际环境、保存状态与产物引用 |
| `tasks/precheck/task.py`、`gate.py`、`timing.py`、`performance.py` | 独立预检入口、正式任务调用、阶段计时和候选比较 |
| 项目根的 `experiment/` | 按数据集、模型、任务、实验名称和单次运行标识组织产物。实验名称 `subname` 使用一至三个具体词，说明实验或探索对象 |
| 单次运行的 `config.yaml` 或项目等价文件 | 保存实际生效值，清单指向该文件 |
| 运行目录的 `metadata/manifest.json` 或项目等价入口 | 定位本轮实际配置、输入、环境、状态、故障和产物 |
| 运行目录的 `logs/`、`reports/`、`artifacts/`、`tmp/` | 按需保存过程日志、可读结果、模型产物和临时诊断。检查点归其实际写入与读取入口 |
| `scripts/`、`tests/` | 人工操作脚本调用正式实现。需要持续回归的行为检查才进入测试目录 |

## 配置维护

1. **定位生效值。** 从项目默认入口和实际命令追到配置合成代码，查清参数的来源、覆盖顺序和实际读取字段。项目可以用配置组组合一套默认配置，默认值集中在其负责位置。核对受默认值变更影响的正式任务和预检，使用项目支持的只读方式查看合成结果。
2. **按用途修改。** 项目通用的默认值改在 `conf/` 的负责位置。单次探索通过正式命令覆盖参数，或在 `experiment/<数据集>/<模型>/<任务>/<subname>/` 保存该实验专用的输入配置。用描述实际用途的 `subname` 组织这类运行，项目默认配置保持原有用途。例如，所有分类运行统一收紧默认预检预算时改默认配置，单独比较批大小时在实验参数中覆盖。
3. **记录运行时的配置。** 运行入口将实际选中的组件、合并后的默认值、显式覆盖、已解析的输入路径和设备写入该次运行的 `config.yaml` 或项目等价文件，并让清单指向它。使用项目的正式入口确认设置传给了实际读取者，并按本次授权选择只读检查或有界预检。配置维护的授权和启动训练的授权分别按用户要求处理。
4. **查历史与复跑。** 解释指标或比较运行时，从各自清单读取当时的生效配置。复跑时以原配置为输入，核对源码、数据与环境，保存到同一 `subname` 下的新运行目录。延续原运行依照「跟踪与恢复」。历史配置缺项时记录已查明的来源和具体缺项。

## 执行与结果读取

1. 从用户要使用的结果倒推命令、配方、输入、模型权重和预算。按项目入口查看实际生效配置，记录显式覆盖值、数据输入根和本次运行在 `experiment/` 内的位置。
2. 如果已有对应的独立预检，从正式配方选择有界样本。检查输入、设备、预算、输出位置和任务计算，确认正式任务能用同样的模块与输入。按计划使用或重新生成预检回执。
3. 在独立运行位置执行获准命令。前台记录日志位置，后台按项目已有方式记录会话身份、命令、有效配置、日志和运行目录。记录实际输入身份、代码版本或摘要、解释器、设备及数值条件。
4. 从项目规定的清单或读取入口找到具体结果。确认清单状态对应实际文件，读到所需的特征和解释、生成内容、干预结果、评测指标或训练报告及权重。部分完成时保留已完成成果，并指出缺项和后续读取或计算方式。

## 跟踪与恢复

先把要查的轨迹与原命令、进程或会话、保存的配置、日志、运行清单及检查点对应起来。当前运行索引只指示当前选择，进展以对应运行证据为准。

| 实际情形 | 处理方式 |
| --- | --- |
| 进程仍在运行并有进展 | 跟踪同一进程、日志或指标。按当前任务等待并检查真实结果 |
| 已完成且结果齐全 | 从清单读取产物。需要后续分析时，把同一次运行的配置、输入和结果交给分析入口 |
| 输出缺某一步 | 查明该步的输入和已完成依赖。有正式分段操作时，只补相应步骤并保存来源关联 |
| 训练停在检查点 | 查明任务的恢复参数和加载实现，核对模型、优化器、调度器及恢复逻辑实际需要的轮数、步数与随机状态。核对原配置、数据身份和软件环境，再按授权续跑 |
| 只有最终模型权重 | 用项目已有的加载入口做评测、分析或新运行的初始化。要续训时，先确认是否存在正式支持的训练状态 |
| 运行状态由用户停止 | 保持该决定。读取状态和成果，涉及新启动或恢复时遵循后续明确授权 |
| 缺少证据或路径失效 | 从运行目录、日志和已登记输入继续定位。说明已证实的结果、具体缺项和可执行的处理方式 |

当前会话可按授权持续监控。跨会话执行采用实际可用的调度机制及对应授权。

## 调试与性能

1. 固定问题发生的命令、配置、输入身份、运行阶段和报错日志。沿实际调用确定责任。数据读取与样本问题追 `datasets/`，构造和权重问题追 `models/`，指标和任务计算追 `tasks/`，分发、环境或清单问题追公共运行层。
2. 选择与故障直接相关的最小输入。临时复现放运行资料的临时目录，正规修复进负责文件。涉及结果格式时同时检查下游读者和旧结果；涉及计算时使用同一代表样本及同一指标对照。
3. 性能从有界预检测准备、读取或等待、设备传输、计算和保存。异步设备在计时边界同步。记录实际配置、样本、预热、重复、环境、资源峰值与最长阶段。只比较同一输入、工作量和结果判据下的候选，分别说明局部开销与端到端影响。
4. 通过获准的正常入口确认修复或候选效果。错误记录说明已知原因、影响及定位方式，报告说明哪些用例和环境已经覆盖。长期检查进入原有测试分组，临时手段按项目惯例收尾。指标、预算或历史可比性变化按用户决定处理。

## 参考项目中的操作

在 CUB 模板，以 `python -m cub_template precheck --subname offline_check --set dataset=synthetic --set runtime.device=cpu` 运行离线预检。程序自动把结果写入项目根的 `experiment/`。命令返回运行目录后，用 `python -m cub_template inspect <运行目录>` 读取 `metadata/manifest.json`，沿输出角色找到实际报告。比较工作进程数使用同一配方的 `benchmark`，其结果由 `tasks/precheck/performance.py` 生成。模板当前导出最终权重，读取者按可用能力判断结果复用和重新运行。

这条命令从 `conf/config.yaml` 取默认值，仅对本次预检覆盖数据集和设备。运行目录的 `config.yaml` 保存合并结果，清单的 `effective_config` 字段指向该文件。复跑时可将该文件传给 `--config`，同时提供 `--subname`。
